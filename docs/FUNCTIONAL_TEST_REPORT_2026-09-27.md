## 发现并修复的问题

**空闲探测会被重试插件重复发送。** `connection-status.ts` 发起的端点探测带有 `x-opencode-conn-probe` 标记，目的是根据第一次 HTTP 响应判断端点是否可达。原来的 `retry-forever.ts` 封装了全局 fetch，却没有识别这个标记。用本地模拟的 HTTP 503 和最多 3 次尝试重现时，一次探测实际发送了 3 次。默认不限次数时，若端点持续返回可重试的 5xx，探测可能一直重试到超时，进而把有 HTTP 响应的端点误报为不可达；这是根据调用链得出的风险，未对真实服务商制造故障验证。

现在重试层遇到该标记会原样转发请求，不对响应或网络错误重试。新增测试覆盖普通 `fetch` 参数、`Request` 参数及两个插件的两种加载顺序；正常模型请求的 503 重试测试仍通过。

## 下一步怎么改

| 优先级 | 修改建议 | 依据与验收方式 |
|---|---|---|
| 高 | 给 OpenCode 2.x 增加真实运行时验证。 | 当前 2.x 语言模型钩子只用模拟模型测试，本机安装的是 1.18.31。应在隔离的 2.x 环境中验证插件加载、首段输出前故障重试、输出后的故障传播，以及用户中断不自动续接。 |
| 高 | 为 1.x 重试明确限定适用请求。 | 当前 fetch 封装除探测标记外，对所有 URL 使用同一重试规则。先核对 OpenCode 实际服务商请求的路由，再让无关的本地或元数据请求保持原行为。验收测试应同时证明“服务商 503 会重试”和“无关请求 503 只发送一次”。不能仅按配置中的 `baseURL` 生硬过滤，以免漏掉没有显式配置地址的服务商。 |
| 中 | 补上“响应头已返回、流式正文随后停住”的受控测试，再决定如何监测。 | 1.x 的在途计数收到响应头就结束。此后若没有输出事件，现有静默判定可能漏报。应先用可暂停的本地流复现，再根据会话事件与请求生命周期设计提示，避免把工具等待当作模型故障。 |
| 中 | 给状态 JSONL 增加大小上限和轮转。 | 文件持续追加；查看器目前只读末尾。应在保留现有历史的前提下实现轮转，并测试写入期间的完整行、重启后继续写入以及查看器读取新文件。 |
